# 样本周期（Sample Cycle）领域重构说明

## 1. 背景与问题

岩心管理相关台账此前各自维护「同一样本能不能进入下一环节」的判断：

| 台账 | 旧判断位置 | 旧口径问题 |
| --- | --- | --- |
| 岩心台账（所属钻孔、取样深度） | `services/core.py` | `送样分析` **无任何前置校验**，待编录/已编录都能直接送样 |
| 送样清单 | `services/sample_registry.py` | `确认收样` 无在途前置；`登记报告` 可越过化验直接出报告 |
| 化验待办 | `services/assay.py` | `录入结果` 无签收前置，样品未到实验室也能录入 |

三套独立状态机对同一物理样本得出三个互相矛盾的结论（种子数据
`CORE/SAMP/ASSA-0002` 即为实例：岩心「已编录」、送样「已收样」、化验「已录入」）。

## 2. 目标形态

* 统一的**样本周期**领域能力：一个物理样本 = 一个周期 = 一个阶段；
* 三处台账不再自行裁决，只读取领域基于统一阶段推导出的可用性结论；
* 判断结果通过读模型投影**回写**岩心台账、送样清单、化验待办；
* **既有接口形态全部保留**（路径、出入参、动作名、`(entry, message)` 返回结构）；
* 新旧读写路径可灰度（legacy → shadow → dual）、可按批次回滚；
* 迁移以既有确认阶段为初始基准，历史裁决原样留痕；
* 回填期间双读校验；转换不成功绝不部分写入；同一批次重跑结果完全一致。

## 3. 阶段与阶段责任组

阶段主轴（`app/sample_cycle/stages.py`）：

```
已登记 → 已编录 → 深度复核通过 → 待送样 → 送样中 → 已签收
      → 化验中 → 化验完成 → 归还在途 → 已闭环
反向：深度复核驳回（→补录后重新编录/复核）
      样品退回（送样/签收后 → 待送样）
      化验退回（化验中 → 化验退回 → 重送/重化验）
```

每个阶段归且仅归一个责任组，跨组裁决在流转表层面直接拒绝：

| 责任组 | 负责阶段 | 唯一可裁决的问题 |
| --- | --- | --- |
| 岩心台账组 `core_ledger` | 已登记、深度复核驳回 | 建档、地质编录是否完整 |
| 取样深度复核组 `depth_review` | 已编录 | 所属钻孔与取样深度是否放行送样 |
| 送样组 `dispatch` | 深度复核通过、待送样、化验退回 | 可否安排送样、退回样品处置 |
| 化验组 `lab` | 送样中、已签收、化验中 | 可否签收、可否录入/完成/退回化验 |
| 归档组 `archive` | 化验完成、归还在途、已闭环 | 可否归还、闭环 |

统一可用性三元组（`policy.availability_triple`）由同一阶段推出，三处天然同源：

* 岩心台账「样本可用性」：复核通过后才 `可送样`；
* 送样清单「样本可用性」：复核通过后 `可安排送样`，在途/签收后不可重复安排；
* 化验待办「样本可用性」：实验室 `已签收` 后才 `可化验`。

## 4. 幂等事件与事件溯源

* 周期状态不由台账字段决定，而由**事件流归约**得到（`sample_cycle_event` 表）；
* 事件类型见 `events.py`：建档、编录、复核通过/驳回、送样、签收、拒收、
  开化验、化验退回/完成、归还、闭环，以及迁移专用的
  `legacy_ruling`（旧裁决留痕）与 `migration_baseline`（初始基准）；
* **命令幂等**：带 `idempotency_key` 的请求按（周期、事件、幂等号）去重，
  同业务意图重放（即使阶段已前进）直接返回既有事件，不重复流转、不重复回写；
  不带幂等号的重复提交按（周期、事件、裁决阶段）自然键去重；
  驳回后再提交、退回后再送样因裁决阶段不同而合法地成为新事实；
* **迁移幂等**：迁移事件按内容哈希寻址（批次号 + 周期 + 台账 + 旧裁决 +
  基准阶段全部进哈希），重跑同一批次逐条命中、不新增事件。

## 5. 事务边界（`store.transaction()`）

快照式事务（支持嵌套），在内存存储里等价于数据库单事务：

| 场景 | 事务范围 | 失败行为 |
| --- | --- | --- |
| 一条业务命令 | 合法性校验 → 追加事件 → 归约阶段 → 三台账投影回写 | 整体回滚，无事件、无半回写 |
| 新建岩心样本 | 台账行落表 → 建周期首事件 → 首次投影 | 整体回滚 |
| 一个迁移批次 | 全部周期的事件追加 + 回写在同一事务 | 任一周期失败整批回滚（strict 下发现矛盾即拒） |
| 批次回滚 | 删批次事件 → 恢复台账行镜像 → 解除绑定（仅首个基线批次删周期） | 批次后已有业务事件时**拒绝删历史**，要求走补偿命令 |
| 模式切换 | meta 表追加审计行 | — |

## 6. 读模型投影与旧接口兼容

`projection.py` 把周期阶段映射回三张表原有的状态词汇与字段：

* `core.status/pending/abnormal/样本状态` 沿用旧词汇（待编录/已编录/送样中/已归还），
  新增 `周期阶段`、`样本可用性` 两个字段；
* `sample_registry`、`assay` 同理（投影是纯函数，重跑输出完全相同）；
* 旧 REST 路径、动作名、分页/筛选/导出全部不变；三个 `actions` 端点同时
  兼容前端历史上的 `{"action": "…"}` 与包裹式 `{"values": {"action": …}}`；
* 岩心侧通过既有 actions 形态新增两个深度复核动作：`深度复核通过`、`深度复核驳回`；
* 新能力只挂在新端点 `/api/sample-cycles/*`（模式、命令、回填、回滚、双读报告）。

## 7. 灰度路径

| 模式 | 写路径 | 读路径 | 用途 |
| --- | --- | --- | --- |
| `legacy`（默认） | 旧三服务原裁决 | 旧字段 | 上线即完全兼容 |
| `shadow` | 旧路径照常写；领域**只试跑不落库**（`dry_run_command`） | 双读 `reconcile()` 暴露分歧 | 观察新口径与旧裁决的差异 |
| `dual` | 事件落库 + 三台账原子回写；旧字段由投影同步维护 | 三表结论同源 + 持续双读 | 新路径为主 |

切换：`PUT /api/sample-cycles/mode`（留痕，可追溯/可回退）。

## 8. 迁移回填

1. `GET /backfill/preview?batch_id=…`：纯推导不落库，列出矛盾样本与
   关联不上的台账行（关联规则：编号尾部数字，如 `CORE-0002 / SAMP-0002 / ASSA-0002`）；
2. 基准：每条台账行按其**既有确认状态**反查周期阶段，以岩心主档为锚点；
3. 留痕：每个周期为三台账各写一条 `legacy_ruling`（旧可用性按旧口径原样记录），
   再写一条 `migration_baseline`（归一基准阶段；矛盾明细一并记录，永不覆盖）；
4. `POST /backfill/run`：
   * `strict=true`（默认）——发现三台账确认阶段互相矛盾即拒绝，整批不写；
   * `strict=false`——带矛盾迁移，矛盾在双读报告中持续报红，等待人工处置；
   * 一个批次一个事务，失败整批回滚；批次按 `batch_id` 幂等；
5. `POST /backfill/rollback`：按批次撤销；批次之后已有业务推进则拒绝；
6. `GET /reconcile/report`：双读校验，逐条比对领域结论与三台账当前裁决。

## 9. 代码地图

```
backend/app/sample_cycle/
  stages.py       阶段、责任组、可用性结论常量
  events.py       幂等事件、自然键、内容哈希、旧裁决/基线事件
  policy.py       流转表、命令合法性、统一可用性三元组、旧状态映射与旧裁决复刻
  projection.py   阶段 -> 三台账字段的纯函数投影
  migration.py    对账关联、批次计划推导、迁移事件展开（确定性纯函数）
  service.py      应用服务：命令、注册/挂接、灰度模式、回填/回滚、双读、事务编排
backend/app/services/{core,sample_registry,assay}.py
                  旧服务按模式分流，接口形态不变
backend/app/routers/sample_cycle.py
                  /api/sample-cycles/* 领域端点
backend/app/store.py
                  快照事务（含嵌套）、reset、upsert/next_id
backend/tests/    test_policy / test_service / test_migration / test_legacy_adapters
```

## 10. 运行测试

```bash
cd backend
python3 -m unittest discover -s tests -v
```

> 说明：当前容器没有 pip/FastAPI 运行时（仓库自带 .venv 指向不存在的
> Python 3.14），领域层与服务层刻意只依赖标准库，测试可直接在 Python 3.11
> 上运行；路由层是薄封装，FastAPI 环境就绪后可直接启动。
